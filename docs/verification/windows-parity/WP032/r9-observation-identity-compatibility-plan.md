# R9 compatibility decision proposal — no implementation

Current typed taint merge identity includes route_file (`merge.py:85-95`). Its normalized Signal stores route_file only as a property (`models.py:1153-1167`); `signal_provenance._identity` hashes kind/label/sink file/sink line and no taint discriminator (`39-44`). Thus two distinct route files can become one normalized observation with a route_file conflict. That conflict remains honest candidate evidence, but the current observation ID cannot identify one exact typed chain.

Changing `_identity` alone is unsafe: `merge_normalized_signals` always writes a newly computed observation ID (`75`), including imported stored observations; `normalized_view` invokes it on stored plus synthesized records (`100-125`). An old normalized observation may already have lost which origin belonged to which route file. It must not be split or aliased by guessing. `finding_presentation.py:68-71` exposes observation IDs as candidate references; broader review/evidence consumers may persist references outside these source files. Existing saved artifacts must remain byte-identical.

Proposed additive migration boundary, pending explicit schema decision:

1. Add an optional explicit observation identity version on newly produced normalized observations; absence denotes legacy, not an implicit upgrade. New taint identity uses a versioned canonical tuple with route_file in addition to the existing sink/method/path identity. Non-taint IDs remain unchanged. Do not change typed taint merge or R3 score producer identity.
2. Separate fresh production canonicalization from stored-observation import. Existing nonempty stored observation IDs and existing origins/conflicts remain unchanged on import, display, export and normalized-view composition. Imported legacy IDs do not silently acquire a new version, producer authority or exact-chain meaning.
3. Retain legacy records with ambiguous/conflicting route_file as legacy ambiguous candidates. Do not manufacture a new ID for each conflict value: source-to-value pairing was lost. Newly captured typed chains may produce separate new-version observations, but their coexistence does not justify legacy-to-new aliases.
4. Citation resolution first uses the exact stored selected-generation ID. A legacy citation can still reference its original legacy observation in that generation. It cannot resolve through a newly recomputed ID or numeric/file similarity. If the original record is absent, return missing; if its route ownership is ambiguous, expose that limitation. No alias table is needed for the first migration slice.
5. Cross-version dedup must not merge a legacy ambiguous record into one arbitrary new observation. Define a version-aware grouping key before implementation; retaining both with explicit version/scope is safer than claiming their equivalence. Analyzer admission is a distinct trust boundary: existing rejection/rebinding of child-claimed IDs must remain intact.

Required focused cases: two fresh typed chains differing only route_file yield distinct IDs under all input orders; same full chain corroborates; legacy stored ID and existing citation survive round trip unchanged; legacy conflict record is not split; absent old citation stays missing; mixed legacy/new records do not invent aliases; duplicate IDs/conflicting payloads remain ambiguous; non-taint IDs unchanged; isolated child-claimed IDs remain untrusted; no fixture rewrite. Compatibility inventory must cover normalized-provenance, merge/conflict, incremental, snapshot, presentation and AI/reference export fixtures before canonical approval.

This plan deliberately requires a schema/import-boundary decision rather than an unversioned hash change. No R9 source, fixtures or stored artifacts have been edited, and no migration/runtime verification is claimed.
