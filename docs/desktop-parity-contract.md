# Desktop parity contract — WP002 frozen current boundary

Status: **WP002 schema 1.1 boundary frozen by integrator on 20 October 2026; additive WP004 schema 1.2 boundary under integration**. WP001 baseline, schema/defaults and expected values were reviewed; the frozen validator still passes 266 checks without byte changes. This is a new deliverable under the active Windows parity plan. It preserves Windows M3 acceptance and adds no release or runtime acceptance claim. Fleet and future AI fields remain outside this boundary until WP014/WP018 add versioned fixtures and consumer evidence.

Run `python fixtures/desktop-parity/validate.py` from the project environment. `prepare.py` deliberately regenerates synthetic JSON and the SHA-256 index after an approved contract change; validation is read-only and must run before regeneration when investigating drift. JSON is UTF-8, ordinary objects/arrays and language-neutral values for Python/C#/Swift; hashes cover exact on-disk bytes, including final newline. Manifest IDs are repository-relative POSIX paths. The index is not an engine publication manifest. Existing maintained workflow/run-contract files are referenced in place, never relabeled or rewritten.

## Current boundary

Authority is current `run_contract.py` and `provider_options.py`, with checked-in schemas. Current request schema is `1.1`; previous supported schema is `1.0`. A future `99.0` request must fail validation. Schema-less data is a saved-report import, **not a legacy request**. Imported reports do not gain verified artifact readiness or policy provenance. Unknown additive envelope/options metadata is currently ignored by core; provider extra fields are forbidden. This existing behavior does not authorize unsupported requested features: WP003/WP004 must fail unsupported explicit options before dispatch.

Defaults are serialized explicitly in `request-current.json`: recall/strict/no-suppress/CVE false, secrets history 0 (0..10000), scan timeout 600 seconds (1..86400), empty modules means Automatic. Provider defaults: AI disabled, openai, literal local LM Studio endpoint/model, 8 calls (1..64), 600 seconds (1..3600), 32000 output tokens (1..256000). Sentinel values in `request-sentinels.json` differ from defaults for every current field. Provider matrix covers openai/claude with AI on/off at model-validation level only; it makes no claim all configurations dispatch successfully.

Review/Hunt/Hunt+verify/Remediate/Triage, jury, effort, fast/backend, suppress_file, baseline policy, resource knobs and fleet requests are **design pending WP004/WP014/WP018**. They are not invented as accepted fields in schema 1.1. Every newly approved field needs a nondefault sentinel, supported combination table, units/range/network declaration, and consumer/service round-trip before freeze. Current fixtures cannot establish those future service mappings.

### Additive schema 1.2 options boundary

WP004 leaves every schema 1.0/1.1 fixture and default unchanged. Schema 1.2 adds exactly seven request option fields with additive fixtures under `tests/fixtures/desktop-options-v12/`: `baseline`, `suppress_file`, `fail_on_new_high`, `fail_on_new_suppression`, `strict_suppressions`, `isolated_analyzers` and `time_budget_seconds`. Null paths/time budget and false booleans are the defaults; sentinels bind both absolute paths, all booleans true and a 17-second time budget. The existing `timeout_seconds` sentinel is also nondefault so wall-clock scan timeout and analysis time budget remain distinguishable.

Both path fields require absolute local paths and map through the existing scan application service. The three policy/suppression booleans, isolated analyzer flag and bounded analysis time budget map to existing `AnalyzeOptions`; the desktop worker does not implement a parallel scoring or scan path. Incremental, AI-mode tuning and fleet fields remain unsupported here because the current application-service mapping does not carry them. Raw validation rejects known aliases for those unwired requests before repository parsing or dispatch, while unknown additive envelope metadata retains prior compatibility behavior.

Progress and terminal envelopes echo the request schema for 1.0, 1.1 and 1.2. The Windows `EngineProtocol` accepts all three output versions; its native producer remains on 1.1 until the Windows options UI actually emits 1.2 fields. This addendum is deterministic contract evidence only: it contains no live provider call, real scan, GUI acceptance or release-package proof.

### Additive schema 1.3 AI boundary

WP014 keeps the default request schema at 1.2 and requires explicit 1.3 negotiation for provider `mode`, `jury_votes`, `effort`, `speed` and `backend`. Supported modes are `none`, `review`, `hunt`, `hunt_verify`, `remediate` and `triage`; capabilities expose the exact per-schema fields, mode list, ranges, provider/model restrictions and requested-to-mapped effort behavior. Legacy provider bytes/defaults remain unchanged. Unsupported mode/enablement conflicts, jury use outside Hunt+verify, unsupported fast/model combinations, CLI backend without enforceable output cap and fleet AI fail before provider dispatch.

The existing publisher-bound run manifest carries `desktop_ai` availability as `not_requested`, `unavailable`, `fallback`, `partial` or `completed`, bound to outputs created by that run. These states do not turn model prose into a deterministic finding. Review/Remediate/Triage use the same captured-reference ID validation; Hunt retains its existing citation semantics. One inherited ledger covers retries and jury passes, and unknown usage remains unknown. Windows WP015 must negotiate 1.3 and extend its protocol consumer before emitting these fields; WP016 owns presentation and WP017 owns real local-model evidence. The frozen WP002 bytes and additive 1.2 fixture bytes remain unchanged.

## State, identity, report semantics

`events.json` gives queued → running 1/4 → cancelling 2/4 revisions. Duplicate/stale revisions, cancelling regression, cross-run/repository/generation events and terminal regression must not update a selected run. Analyzer done is not run completion. Completion with policy failure is successful analysis; failed/cancelled cannot publish ready artifacts. `identities.json` supplies two generations for repo A and repo B with the same display basename as A (`identity-paths.json`); identity must never derive solely from the basename. Paths are synthetic identity values, not prerequisites to create directories or scan them.

The manifest pins counts and exact source order of every supplied findings/suppressed/path/exploitability array. Preserve source IDs, core score/order, confidence, evidence basis and limitations; consumers do not rescore or infer missing associations. Missing optional sections are unknown/unavailable, empty arrays are explicitly empty, filtered lists retain source total. Synthetic empty reports remain schema-less legacy imports and prove no complete scan. Existing workflow fixtures cover active/suppressed findings, long Unicode paths, conflict/unknown evidence, partial coverage, title/line drift, and expected diff classifications.

`report-nonempty-legacy.json` is a byte-identical copy of the maintained `tests/fixtures/ui/juice-shop-report.json`. It is a legacy UI fixture, not a freshly executed scan or proof that its historic rows satisfy current typed core models. `report-partial-legacy.json` is its documented projection: dependency/CVE sections removed and a synthetic partial limitation supplied. `report-expectations.json` pins exact rows, count, identity fields and source order for findings, suppression, paths, exploitability, attack surfaces, routes, secret hints, dependencies, taint, vulnerabilities, workflow issues and analyzer errors. Rows without IDs retain source keys; no IDs are fabricated. AI review text is explicitly empty, provider metadata is missing, analyzer errors are explicitly empty; these states never prove a completed AI call or installed analyzers. The historical aggregate diff counts remain as supplied and must not be recomputed from the two fixture findings.

Failure/cancel/policy failure are run terminal envelopes, not fabricated report fields: execution failure/cancellation publish no ready report; policy failure is completed analysis with ready artifacts. Existing maintained partial workflow reports additionally exercise diff coverage. New fleet and mode schemas remain pending their owning implementation tasks.

`feature-map.json` maps every F01–F26 to fixture references and an explicit platform/manual procedure with owning WP task. Renderer hostile cases, real watch, publication/export/retention, credentials, distribution, native visual/accessibility and participant acceptance require actual host evidence. No fixture pass proves those activities or a live provider response.
