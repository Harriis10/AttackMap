**Planning baseline:** 15 October 2026, core checkout `4366b40` plus the working tree reviewed that day.  
**Product direction:** an evidence-first defensive analysis engine with beautiful, understandable, native-first Windows and macOS applications.  
**Execution tracker:** [AttackMap implementation TODO](implementation-todo.md).

Correct misleading evidence and stale reports, establish a reliable engine contract, and develop the two desktop experiences around that contract. ## Decisions and boundaries

- **Confirmed design preference:** native-first experiences tailored to Windows and macOS. Share concepts, evidence semantics, contract fixtures, and brand identity. Give each platform its own controls, navigation treatment, menus, shortcuts, typography, and window behavior.
- **Keep the modular monolith:** the CLI, CI integration, and desktop clients use the same analysis policies. No service split, broker, event-sourced storage, or cloud dependency is needed for the desktop redesign.
- **Preferred desktop direction:** a thin WinUI 3 Windows application and the separate SwiftUI macOS application. Validate the Windows migration with a small working slice before committing to a full port. The existing Windows WebView2 application remains available during migration.
- **Retain local-first operation:** opening reports and running deterministic analysis require no account. Network features such as CVE enrichment and AI must be identifiable, optional, and governed by explicit settings.
- **Keep analyzers focused on extraction:** provenance, conflict resolution, global scoring, and report semantics remain core responsibilities.
- **Introduce changes incrementally:** additive contracts, compatibility fixtures, a desktop preview channel, and a supported rollback path precede retiring existing implementations.

The existing [October 13 review](architecture-review-2026-10-13.md) and [macOS MVP plan](macos-gui-plan.md) are historical inputs. Their implementation claims and exclusions are not the current acceptance baseline. In particular, public macOS signing and notarization are new release goals here. The current source of the separate `mlaify/AttackMap-mac` repository was not audited in this review; M2 starts by establishing its actual capabilities.

## M0 Restore correctness

### C01 Release baseline

**Success:** zero unexpected failures and zero collection errors in the complete supported core test matrix. Every skip has a recorded platform or dependency reason; required release checks cannot be skipped. Fix the hunt, remediate, and triage imports at an intentional API seam. The package, CLI, release metadata, README, and project facts report the same release identity. Windows receives core test coverage as well as frozen-build smoke coverage.

**Proof:** clean-checkout commands, Python and dependency versions, CI links, and wheel/frozen version outputs. Start with Python 3.11 to 3.13, which the reviewed CI uses, and record the supported OS matrix. A change to supported versions needs a documented compatibility decision.

### C02 Guard safety

**Success:** recognized safe predicates suppress a flow only when their documented semantics, branch polarity, and control flow prove the sink receives a guarded value. Unknown predicates remain uncertain. Paired safe/unsafe fixtures cover positive and negated conditions, early returns, exceptions, enclosing branches, nested branches, reassignment after validation, and unrelated-variable checks in every implemented guard frontend. Reversing a protective guard must never silently preserve its sanitized classification.

**Proof:** the original reversed-condition reproduction plus the complete paired fixture matrix. Any unsupported form is reported conservatively and cannot suppress a finding merely because its text resembles a guard.

### C03 Scoped evidence

**Success:** an unrelated worker hint, datastore, outbound call, or auth hint does not change a route's own exposure or control claims. Unresolved ownership is explicitly unknown. Static parsing never produces a runtime-observed label. Every output format and AI prompt uses the same evidence classification; a downstream formatter cannot strengthen a claim.

**Proof:** before/after fixtures varying one unrelated file at a time, including `/internal` and `/debug` routes without deployment evidence. The report retains separately labeled repository context without presenting it as a route-level fact.

### C04 Fresh results

**Success:** reports are keyed by repository and immutable generation identity. Across 100 scripted scan sequences, no view shows a prior generation as current. Cover rapid completion between polls, slow scans, navigation during a scan, delayed responses, failed rescans, and switching repositories. An older successful report may remain visible only with its timestamp and an explicit previous-result label.

**Proof:** frontend integration tests using the actual state/cache adapter, including the original completed → running → completed reproduction. Out-of-order responses cannot overwrite a newer state, and polling has at most one active request per state stream.

### C05 Scan isolation

**Success:** three consecutive unchanged scans have identical normalized findings and source-file coverage when output is at the repository root, below it, or outside it. Generated artifacts do not become input evidence. A user-owned file with the same basename as an artifact remains analyzable unless positively identified as generated output.

**Proof:** manifest-driven output-exclusion tests, including the existing failing root-output test, legacy artifact names, and a same-name legitimate source fixture.

### C06 Fleet formats

**Success:** a fleet of two small repositories completes with identical normalized results for serial and two-worker execution for every supported presentation format. Internal worker interchange is always machine-readable regardless of requested rendering. Source and frozen Windows execution both work, including paths with spaces and non-ASCII characters. One failed child produces an explicit per-repository failure and preserves successful siblings.

**Proof:** the original Markdown/fleet reproduction, format-matrix tests, and a packaged-worker smoke test. No worker invokes a frozen executable as though it were a Python interpreter.

### C07 Honest AI and privacy

**Success:** missing, timed-out, and malformed individual votes count as abstentions, never refutations. A run with no usable votes or no strict majority of its planned votes resolves to an explicit inconclusive state. A model majority is labeled as model assessment, not confirmed exploitability. Settings and help explain which optional features contact a service and which inputs they send. AI is off for a fresh installation. Credentials never appear in reports, logs, or diagnostic exports.

**Proof:** consensus truth-table tests, provider-failure fixtures, sentinel-secret checks, and copy review across CLI, Windows, macOS specifications, and documentation. Existing useful local-only flows remain available.

## M1 Stabilize engine contracts

### C08 Run protocol

**Success:** publish versioned schemas and fixtures for a scan request, progress event, terminal result, and artifact manifest. Include run ID, repository identity, generation, monotonic state revision, schema version, execution outcome, policy outcome, and artifact readiness. States distinguish queued, running, cancelling, completed, failed, and cancelled. A policy threshold breach is a completed analysis with a failed policy outcome. Sub-analyzer `done` events never mean the whole run completed.

**Proof:** CLI and client contract tests accept current and immediately preceding supported schema versions, ignore additive unknown fields, and reject incompatible major versions with an actionable message. Legacy schema-less reports have an explicit import adapter or clear unsupported result. Desktop consumers publish their supported schema range independently of app version.

### C09 Process supervision

**Success:** one supervisor owns process creation, timeout, cancellation, bounded logs, and process-tree cleanup. In 50 start/cancel cycles per platform, UI acknowledgement is at most 250 ms at p95 and the controlled worker tree exits within 5 seconds, including a child that ignores graceful termination. Twenty simultaneous start requests for the same exclusive scan slot launch exactly one worker. Cancellation cannot release that slot until termination is verified.

**Proof:** OS process inspection and race tests on Windows and macOS. Use a 3-second graceful interval followed by a 2-second forced-termination allowance. A cleanup failure is visible and blocks an unsafe restart. Fleet admission is bounded by available worker slots, and cancelled queued work never starts.

### C10 Atomic results

**Success:** CLI, desktop, and fleet use the same generation publisher. A generation becomes current only after required files and schemas validate. Fault injection at every publication boundary leaves either the complete previous generation or the complete new generation readable, never a mixture. Error and cancellation runs record a terminal diagnostic manifest without replacing a valid current result. Publication duration is present in finalized timing data.

**Proof:** filesystem failure, interrupted-write, invalid-artifact, and process-exit tests on both operating systems. Existing CLI output filenames remain supported through a documented compatibility view or export step; consumers never need to infer success from a stderr phrase.

### C11 Source provenance

**Success:** every new normalized observation carries an immutable observation ID, analyzer name/version, source role, location or explicit location-unavailable reason, and evidence kind. Conflicting auth or exposure observations survive merging and appear as conflicts. Duplicate observations retain corroborating provenance without double-counting files. Merge does not mutate analyzer-owned input objects. Older plugins are adapted with explicit unknown metadata.

**Proof:** multi-analyzer conflict fixtures, permutation-invariance tests, input-immutability tests, and unique-file coverage assertions. Extend the existing normalized model and signal bridge; avoid a parallel evidence system.

### C12 Evidence ownership

**Success:** one core policy classifies production, test, fixture, mock, example, generated, and unknown sources. Route-to-service, route-to-datastore, and inter-service relationships are either backed by evidence IDs or explicitly marked candidates. Missing auth evidence stays distinct from observed anonymous access. For every displayed high-priority finding, users can identify the observed facts, inference steps, and unresolved assumptions.

**Proof:** source-role fixtures spanning supported path conventions, route ownership counterexamples, and cross-format golden reports. Ranking tests verify the intended effect of confidence and source quality without treating scores as calibrated probabilities.

### C13 Finding identity

**Success:** changing a title or recommendation does not turn an unchanged finding into new/resolved findings. Stable identity uses rule and entity/location semantics with a documented collision policy. A migration adapter reads existing baselines and suppression references. Unmappable records are reported for review rather than silently dropped. Renames are either resolved by an explicit mapping or visibly treated as uncertain.

**Proof:** title changes, nearby line insertions, duplicate routes, moved files, and old-baseline migration fixtures; suppression reasons and provenance survive round trips.

### C14 AI boundaries

**Success:** every provider call reserves a call, time, and token allowance before dispatch, including retries, generation, and verification. Tests with a fixed ledger prove zero calls begin after allowance exhaustion and requested output limits fit remaining reservations. Unknown provider usage is marked unknown, not zero; a dollar ceiling is an estimate unless the provider supports enforceable billing controls. Evidence references resolve to allowed IDs and exact snapshot spans; basename or substring matches cannot validate a citation. Reference validity remains distinct from whether evidence supports a claim.

**Proof:** fake-provider tests for multi-round budgets, retries, cancellation, missing usage, malformed citations, and unsupported claims. Source excerpts are minimized and redacted. Embedded repository instructions cannot change tool permissions, recipients, or analysis policy. AI cannot rewrite deterministic findings or apply remediation without a separate user action.

### C15 Architecture seams and diagnostics

**Success:** the shared application service accepts typed requests and returns typed results without importing Typer or desktop modules. Presentation translates requests and renders results. Analyzer modules do not import report rendering or scoring policy. Structured local diagnostics include run/stage IDs, durations, analyzer versions, input coverage, resource-limit events, and terminal errors for every attempted run, including startup failures when the output directory is writable.

**Proof:** import-boundary checks and an end-to-end fixture exercised through CLI and both client adapters. Diagnostics distinguish execution failure, degraded coverage, and policy failure; default logs contain no source excerpts or secrets. Do not claim a remote observability service is needed to satisfy this gate.

## M2 Design native desktop experiences

### C16 Platform inventory

**Success:** inventory the current Windows app and the actual macOS repository at recorded commits. List every supported workflow, engine option, schema assumption, credential mechanism, and distribution requirement. Publish a parity matrix with present, missing, and intentionally different states. Select supported OS versions and CPU architectures, with a real test host or runner for every claimed target.

**Proof:** recorded inventory and platform-support decision. The historical macOS 15 minimum is a starting input, not proof of current support. Unverified macOS functionality stays unverified until exercised.

### C17 Native design foundations

**Success:** deliver separate Windows and macOS design specifications with light, dark, and system appearance; platform typography; spacing; elevation; icon usage; focus/selection states; semantic severity colors; density; and motion. Cover at least 12 components: navigation, toolbar, button, input, table/list, filter, status badge, banner, dialog/sheet, progress, code evidence, and empty/error state. All application-controlled colors and spacing map to named tokens or a documented visualization palette.

**Proof:** inspectable component specimens for both platforms and a design review with no unresolved blocking inconsistency. Keep native window controls and standard system dialogs. Severity always has a textual label; decorative effects must preserve contrast, legibility, and reduced-transparency preferences.

The visual goal is a calm, polished engineering workspace: clear hierarchy, useful density, generous separation between unrelated content, and a restrained accent color. Use native materials selectively around navigation and chrome. Evidence, tables, and source text need stable, readable surfaces.

| Area | Windows direction | macOS direction |
| --- | --- | --- |
| Shell | Fluent navigation and command patterns, standard window behavior, Windows system typography | Native sidebar and split views, macOS toolbar and menu bar, system typography |
| Common actions | Discoverable commands, context menus, Windows keyboard conventions | Menu commands, contextual actions, Command-key conventions and a standard Settings window |
| Findings | Virtualized list/table with a persistent evidence detail area | Native list/table with a detail pane or inspector |
| Platform integration | Native folder/save dialogs, Explorer reveal, protected credential storage | Native open/save panels, Finder reveal, Keychain integration |
| Brand | Shared naming, semantic severity meanings, icon concepts, and restrained accents | Same product identity with macOS-specific sizing, materials, and interaction |

These directions follow the goals of [Fluent design principles](https://fluent2.microsoft.design/design-principles), [Windows navigation guidance](https://learn.microsoft.com/en-us/windows/apps/design/basics/navigation-basics), and [Apple guidance for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos). They do not require the two apps to look identical.

### C18 Navigation and screens

**Success:** organize the product into six primary destinations: **Overview, Findings, Architecture, Inventory, Reports, and History**, with Settings in its platform-standard location and a persistent workspace/repository selector. Map every existing capability to this structure or record an explicit deferral. Exploitability is presented as explained prioritization within Findings; raw artifacts belong in Reports. Advanced scan options are progressively disclosed.

**Proof:** clickable flows cover nine key views: start workspace, overview, findings list, finding detail, architecture, inventory, reports, history, and settings. From a selected repository, the default scan starts with one primary action. Selecting a new repository and starting requires at most three application steps: choose repository, confirm location, start scan. A selected finding's evidence and recommendation are reachable in at most two further actions.

| Destination | User question | Primary content |
| --- | --- | --- |
| Overview | What deserves attention in this run? | Prioritized next actions, changes since the baseline, positive controls, coverage and uncertainty |
| Findings | What is the concern and why should I believe it? | Search/filter list, explained priority, source evidence, recommendation, and triage |
| Architecture | How do services and trust boundaries relate? | Evidence-backed service map, candidate-edge distinction, and equivalent navigable list |
| Inventory | What did AttackMap discover? | Routes, dependencies, datastores, integrations, and analyzer coverage |
| Reports | What can I read or share? | Defensive review, exact-run export, and advanced raw artifacts |
| History | What changed between analyses? | Dated generations, comparison, baseline selection, and retained/pinned runs |

Required interaction states are first launch, loading, no findings, filtered-empty, partial/degraded result, stale previous result, cancelling, failure with retry, missing analyzer, unavailable AI provider, and incompatible report. Every state has an explanation and a useful next action. Architecture views also have a searchable list representation for keyboard and assistive-technology users.

### C19 Validated prototypes

Windows participant validation is carried into M4 by the 2026-10-15 user decision; it does not block the accepted Windows M3 functional beta. macOS requirements are unchanged.

**Success:** test both native design prototypes with 10 representative participants: five primarily Windows users and five primarily macOS users, including three developers and two security practitioners in each group. For each of the six tasks below, at least 9 of 10 participants succeed unassisted, with at least 4 of 5 succeeding on each platform. No participant sends code externally unintentionally or mistakes a prior result for the current scan.

**Proof:** anonymized task outcomes, elapsed interaction times, observed problems, and design revisions. Exclude scan/provider processing time from task timing. Give a short product introduction, no workflow training, and use the same seeded scenario per platform. Retest a failed task with five new participants on the affected platform; all five must succeed before accepting the revision.

| Task | Completion condition | Time ceiling |
| --- | --- | --- |
| Start analysis | Select the supplied repository and launch a default local scan | 60 seconds |
| Understand a finding | Identify its priority, uncertainty, supporting source, and proposed fix correctly | 120 seconds |
| Understand a result change | Compare two runs and correctly distinguish new, resolved, and suppressed findings | 120 seconds |
| Recover a scan | Cancel a run and start a new run after cancellation completes | 60 seconds of interaction |
| Understand AI disclosure | Identify the provider and data being sent, then leave AI disabled | 60 seconds |
| Share a result | Export the requested review for the selected run | 60 seconds |

Collect a 1-to-5 rating for clarity, visual coherence, and feeling at home on the participant's OS. The median of each rating must be at least 4 on each platform. These are design acceptance thresholds for this study, not population-level claims of usability.

### C20 Technology decision

**Success:** record an architecture decision after a time-boxed, at most 10-engineer-day Windows spike and an at most 5-engineer-day macOS integration spike. Each slice opens a real fixture, renders 10,000 virtualized findings, exposes usable keyboard/screen-reader navigation, launches/cancels a controlled worker, and produces an installable development package. Record startup, memory, packaging effort, missing platform features, and estimated migration work.

**Proof:** source, recordings, measurements, and a migration decision with a rollback plan. Prefer WinUI 3 for the Windows shell and SwiftUI for macOS. If retaining the current Windows host is materially cheaper, it must demonstrate the same native interaction and accessibility gates; changing to a generic shared web shell does not satisfy the chosen design direction by itself.

Microsoft identifies [WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/) as its recommended native framework for new Windows desktop applications. This supports the spike choice; it does not establish that a migration will be cheap. Do not move Python analysis logic into either UI language.

## M3 Deliver desktop beta

### C21 Desktop parity

**Success:** both applications pass the same ten workflow scenarios: open repository, run default scan, configure advanced options, browse/filter findings, inspect evidence, explore architecture/inventory, compare runs, manage a reasoned suppression, export a selected run, and configure optional provider access. Settings persist correctly; semantic results match the CLI fixture. Old configuration/report import is either supported or handled with an actionable migration message and preserved original data.

**Proof:** independently recorded Windows and macOS end-to-end runs against shared fixtures. Native menus, folder/save dialogs, reveal-in-file-manager actions, selection, clipboard, shortcuts, and window restoration work on each supported platform. UI modules contain no alternate scoring or detection policy.

### C22 Scan experience

**Success:** both clients pass C04, C08, and C09. Display the repository, run timestamp, current stage, cancellation state, artifact readiness, and coverage limitations. Do not invent a percentage or ETA for an unbounded stage. Rapid rescans and changing the active workspace cannot cross-wire results. Errors offer retry and a redacted diagnostic path while preserving the previous valid report.

**Proof:** a shared fake-engine suite injects out-of-order events, duplicate events, worker death, policy failure, unsupported schema, truncated output, and missing artifacts. Each case has the same semantic outcome in both clients.

### C23 Evidence experience

**Success:** a finding detail view consistently presents the claim, priority factors, confidence/uncertainty, observed controls, source locations, relevant trust chain, and concrete recommendation. Inference edges are visually and textually distinct from observed relationships. Suppression includes a reason and is reversible. History comparisons distinguish changed coverage from a genuine resolution. Exports identify the exact run and preserve the same evidence labels as the screen.

**Proof:** golden reports and UI tests for conflicting evidence, missing locations, unsupported language, truncated coverage, long paths, and non-ASCII text. No ranking heading implies verified exploitation from heuristic scoring alone. Opening a source location that changed since the scan warns that the live file may differ.

### C24 Accessibility

Remaining Windows manual validation is carried into M4; the functional beta is not certified accessible by this scope decision.

**Success:** keyboard-only users can complete all ten C21 workflows without traps; focus remains visible and unobscured. Narrator on Windows and VoiceOver on macOS expose names, roles, state, reading order, and scan updates. Normal text contrast is at least 4.5:1, large text 3:1, and essential non-text controls 3:1. Labels and evidence remain usable at 200% text size. Motion respects reduced-motion settings; both platforms support their increased-contrast settings.

**Proof:** automated checks report zero critical or serious issues, and manual assistive-technology testing passes every workflow. For retained web surfaces, assess all applicable WCAG 2.2 AA criteria, including 24 by 24 CSS-pixel target sizing with its documented exceptions. For native surfaces, use platform accessibility tools and equivalent task-based checks; a web checker alone cannot certify the native app. Native primary scan/cancel controls target at least 32 logical units in height, with compact control exceptions documented and tested.

Use [WCAG 2.2](https://www.w3.org/TR/WCAG22/) for web criteria and [Apple accessibility guidance](https://developer.apple.com/design/human-interface-guidelines/accessibility) for native review. Record tested scope and exceptions; do not label the whole product compliant based on one automated scan.

### C25 Visual quality

Remaining Windows manual UX/visual validation is carried into M4; existing captures retain their recorded limitations.

**Success:** inspect 72 reference captures: nine C18 views × two platforms × light/dark × two logical window sizes, 1024 by 700 and 1600 by 1000. There are no clipped labels, overlapping controls, unreadable badges, unintended full-window horizontal scrollbars, or unresolved blocking design deviations. Tables and diagrams may scroll within clearly bounded regions. Review all C18 exceptional states separately. System appearance switches live without losing state.

**Proof:** versioned captures, design-spec comparison, and a resolved defect list. Also check Windows 100%, 150%, and 200% display scaling and macOS standard/scaled display modes while maintaining the supported logical viewport. Native components may vary by OS version; visual baselines must identify that version. Repeat the C19 visual ratings on the implemented beta in M4.

### C26 Desktop performance

Windows M3: removed from acceptance by user decision on 15 October 2026; diagnostics are optional. The following targets and proof remain required for macOS only.

**Success targets:** p95 app-ready time at most 3 seconds; p95 report-ready time at most 2 seconds for the reference fixture; p95 filtering at most 150 ms; p95 selection-to-detail at most 100 ms. Combined UI-process memory is at most 500 MiB after loading, excluding the analysis worker and including owned web-renderer processes. After 100 open/close cycles, retained UI memory grows by at most 50 MiB over the warmed baseline.

**Proof:** a versioned fixture with 10,000 findings, 50,000 observations, and a 20 MiB report; publish the generator and checksum. Use an Apple M1-or-better Mac with 16 GiB RAM. Record exact hardware, OS, app, and engine builds. Use 30 fresh-process launches and 30 load trials; interaction measurements use 10 warmups followed by 100 samples. App-ready means the primary action responds; report-ready means its list and first detail are usable. These targets are unmeasured until the spike and beta tests.

## M4 Release and improve detection quality

### Carried forward from Windows M3 by user decision (2026-10-15)

These are M4 work items, not blockers for the accepted Windows functional beta. Preserve existing evidence; perform only outstanding checks and investigate actual failures.

- [ ] C19 Windows study: five representative Windows users, with the original task outcomes and retest rules. Do not substitute agents for participants.
- [ ] C21/C25 manual UX: finish the ten workflow journeys, native dialogs/clipboard/reveal, exceptional states, appearance switching and outstanding visual/scaling review.
- [ ] C24 manual accessibility: keyboard-only completion, focus/Escape behavior, Narrator announcements, contrast, 200% text, high contrast and reduced motion.

The original criteria below retain their intended validation standard. Deferral is not an assertion that they passed. macOS scope remains unchanged. Windows C26 performance qualification is removed, not deferred or replaced by a Windows 10 performance gate.

### C27 Detector evaluation

**Success:** create a versioned evaluation set with at least 30 repositories, 300 positive cases, 300 negative cases, and 10 entirely clean repositories. Cover Python, Node/TypeScript, PHP frameworks, and distributed/protocol-oriented systems. Split by repository, holding out at least 20% before tuning. Every family advertised as supported has at least 30 positive and 30 negative labeled cases; otherwise label it experimental and report its sample count.

Release targets are at least 95% precision and 80% recall per supported high-priority family on the expanded set, with separate held-out results. BOLA and unauthenticated state-change detection must meet those targets before receiving broad quality claims. Define the matching unit and treatment of duplicate/ambiguous findings in advance. Publish TP, FP, FN, sample counts, and uncertainty intervals; no family may disappear from the table because it performs poorly. Preserve all original regression fixtures.

**Proof:** reviewed labels, evaluation scripts, frozen corpus versions, and raw reports. If detector targets are missed, keep that capability visibly experimental or postpone its quality claim. Desktop release can proceed only if this restricted scope is explicit and its supported capabilities pass; no retrospective relabeling of test cases to improve a score.

### C28 Service resolution

**Success:** service identity preserves protocol, host, port, and deployment namespace where known. `auth-api` and `auth-worker` remain distinct unless an explicit alias maps them. Method/path similarity alone cannot resolve a cross-repository destination. Case-sensitive route distinctions survive. Unresolved or multi-match destinations remain candidates and do not create an observed trust path.

**Proof:** fixtures for hyphenated names, DNS suffixes, ports, proxies, aliases, same-path endpoints, and ambiguous destinations. A three-service reference system resolves every explicitly modeled edge correctly and emits no unsupported resolved edges; candidate edges remain separately inspectable.

### C29 Release distribution

**Success:** every advertised OS/architecture combination passes clean-machine installation, first scan, cancel/retry, export, upgrade from the previous supported release, and uninstall. Windows packages are signed; public macOS builds are signed and notarized. Packaged dependencies are recorded, reproducible through a release lock or equivalent manifest, and accompanied by a software bill of materials. Required UI/runtime dependencies are present without a developer environment.

**Proof:** CI artifacts, signature/notarization validation, checksums, and clean-machine run records. Document whether each package bundles the engine or discovers an installed CLI; both paths must enforce the schema compatibility policy. Keep general library dependency ranges separate from exact release-build inputs. Publish a verified previous-version rollback procedure that preserves reports and settings.

### C30 Retention and diagnostics

**Success:** retain the current valid generation and by default the latest 20 completed generations per repository, with a 2 GiB soft storage budget. If the protected current generation exceeds that budget, retain it and show the overage. Users can pin a run; cleanup never removes pinned, active, or current runs. Diagnostic export shows a preview, redacts secrets, and excludes source excerpts by default. Stored credentials use platform-protected storage; an unavailable secure store produces an explicit error, never plaintext fallback.

**Proof:** retention tests at count/size limits, interrupted cleanup recovery, pin/current invariants, and sentinel-secret tests. Sensitive settings never appear in report files. Any loopback control API remains bound locally and rejects unauthenticated or disallowed-origin requests; if retired, verify its listener is gone.

### C31 Watch correctness

**Success:** watch mode observes real source changes, ignores generated output, debounces a burst into one scan, and records a pending dirty state when changes arrive during analysis. After an active run completes, exactly one follow-up scan processes the accumulated burst. Repository switching stops the previous watcher. All repositories in a watched fleet are covered or the UI explicitly restricts watch to one selected repository.

**Proof:** platform-specific filesystem tests for create, edit, rename, delete, output publication, rapid bursts, and changes during a long run. No infinite rescan loop or silent lost change is allowed. Unsupported filesystems produce a visible limitation.

### C32 Beta exit

**Success:** repeat C19 on implemented builds with 10 new participants and meet its task and visual thresholds. Run a four-week beta with at least 12 participants, at least six per platform, and at least 100 completed or intentionally cancelled runs per platform. There are zero unresolved release blockers involving wrong-generation results, data loss, exposed credentials, inaccessible core workflows, or uncontrolled worker processes. All reproducible crashes are fixed or the affected capability is removed from the advertised release scope and re-tested.

**Proof:** participant-consented local diagnostic bundles or manually supplied results, issue dispositions, usability records, and a gate checklist for C01 through C31. No telemetry is silently enabled to satisfy this measurement. Full M4 closes when all supported-scope gates pass; any deferred capability remains visible in the tracker and release notes.

## M5 Scale the local engine

### C33 Consistent snapshots

**Success:** all deterministic passes, fingerprints, and AI excerpts reference one content-identified scan snapshot. If a file changes mid-scan, the engine either analyzes its captured version consistently or marks the run incomplete and retries according to a bounded policy. New/deleted files are detected. No report combines evidence from two revisions without saying so.

**Proof:** mutation tests during indexing, detection, report writing, and excerpt extraction. Snapshot and analyzer/config identities are recorded in the manifest. Shared indexing reduces duplicate reads without removing filesystem safety checks.

### C34 Safe incremental analysis

**Success:** cache identity includes content, analyzer version, schema, configuration, source-role policy, and relevant dependencies. Across 100 generated edit sequences, incremental and full scans have identical normalized findings, provenance, and coverage. Corrupt or stale entries trigger safe recomputation. On the published reference corpus, a 1% source edit has median wall time at most 50% of a full scan; cold analysis regresses by no more than 10%.

**Proof:** differential tests for file rename, deletion, dependency change, analyzer upgrade, config change, and cache corruption, plus 20 measured repetitions per mode on fixed hardware. Ship caching only after correctness equivalence passes. Local SQLite is an option for indexed history/cache if measurements justify it; flat artifacts remain the interchange boundary.

### C35 Resource limits

**Success:** publish finite default budgets and configurable ceilings for accepted source bytes, file count, graph size, worker concurrency, elapsed time, and AI usage. Initial engineering targets are 512 MiB accepted text, 100,000 files, 1,000,000 graph edges, and a 10-minute deterministic-run timeout, with clear user overrides. Every exceeded limit produces explicit partial coverage or a typed failure; no truncated result is represented as complete.

**Proof:** stress fixtures at 10,000, 50,000, and 100,000 files with declared byte/graph sizes. At the default accepted-text limit, a single deterministic worker stays below 2 GiB peak resident memory on the reference host or the default is reduced before release with documented measurement. Admission limits reserve a configurable fleet memory budget. Cancellation remains within C09 under load. Publish p50/p95 stage time and peak memory; do not invent a universal repositories-per-second claim.

### C36 Analyzer boundary

**Success:** define a versioned extraction protocol and an optional isolated analyzer host. A crashing, hanging, noisy, or malformed-output analyzer cannot crash the core or corrupt another analyzer's output. Time, output-size, and memory limits terminate the offending worker with a named partial-coverage result. Default trusted-analyzer policy is explicit; a package name is never represented as cryptographic authenticity or a sandbox.

**Proof:** malicious-behavior test plugins in controlled fixtures, resource-limit tests, and compatibility tests for current official analyzers. Document OS-specific capabilities and filesystem/network restrictions actually enforced. Subprocess separation alone must not be marketed as a security sandbox.

### C37 Delivery efficiency

**Success:** a new contributor can build the core and run its focused suite within 30 minutes, and a supported desktop developer can run the respective fixture-backed app within 90 minutes, excluding prerequisite tool downloads. Three contributors unfamiliar with the relevant component each complete the written setup without undocumented steps. Contract changes run both client fixture suites in CI before release.

**Proof:** onboarding trial records, maintained architecture/contract docs, release-build dependency manifests, and CI links. Track median change lead time and flaky test incidents for eight weeks; fix repeated causes before adding infrastructure solely to improve an unmeasured metric.

## M6 Expand where demand is proven

### C38 Ecosystem depth

**Success:** ship reusable language extraction, framework enrichment, and thin application/protocol overlays for at least three representative stacks: Node/TypeScript services including ATProto, PHP/Laminas/Omeka S, and Python web services. Each has a documented capability matrix, at least 10 production-like fixtures, and explicit unsupported cases. Every new high-priority finding references source evidence and passes the C27 evaluation policy before being advertised as mature.

**Proof:** analyzer/core contract suites and defensive reviews of reference systems with labeled service boundaries, positive controls, and risky chains. Config/infrastructure extraction can add structured observations through the same model; overlays cannot introduce separate global scoring.

### C39 Team product decision

**Success:** decide whether shared history, team triage, and remote fleet execution justify a separate product surface. Collect eight weeks of workflow evidence from at least three teams. Compare local artifact exchange, a shared read service, and supervised remote workers on privacy, administration, reliability, and estimated operating cost. A go decision requires at least two teams with a recurring need the local product cannot reasonably satisfy and an agreed measurable pilot objective.

**Proof:** an architecture decision with demand evidence, deployment/retention boundaries, cost assumptions, and a go/no-go outcome. A no-go closes this decision successfully and defers C40. No SaaS migration is assumed by this roadmap.

### C40 Conditional team pilot

**Success if C39 is go:** implement the smallest chosen shared capability with tenant-scoped authorization, auditable changes, defined data retention/deletion, and isolated remote jobs if jobs are included. Automated tests prove no cross-tenant access for every exposed resource type. Complete a backup/restore exercise with an initial recovery target of at most 4 hours and at most 24 hours of data loss. A 30-day pilot meets its agreed objective and stays within the numeric monthly cost ceiling recorded before implementation.

**Proof:** threat model, authorization tests, deletion/restore records, operator runbook, and pilot/cost report. Do not add event sourcing unless replay/audit requirements exceed ordinary versioned records and audit logs; do not split services without a demonstrated scaling or ownership boundary.

## Migration and release strategy

1. Land small correctness patches with reproductions first. Keep existing CLI behavior unless an explicitly documented correctness change requires an update.
2. Add the run/evidence contracts and golden fixtures; provide adapters for older reports and plugins before switching writers.
3. Build native desktop slices against recorded fixtures, then connect them to the supervised engine. Use one shared contract test corpus across the Python, Windows, and macOS repositories.
4. Port one complete user journey at a time. Maintain a visible parity matrix and a preview channel. Preserve originals when migrating settings, suppressions, and report history.
5. Run both old and new clients against the same report fixtures. Retire the previous Windows renderer only after parity, performance, accessibility, installation, and rollback gates pass.
6. Ship release candidates per platform. A failing macOS gate does not imply Windows passed, and a passing Windows gate does not justify advertising macOS readiness.

Suggested boundaries as the code evolves: `application` for use cases and typed requests, `execution` for worker supervision, `artifacts` for publication and schemas, `evidence` for provenance and ownership, and platform-specific view models for presentation state. Extract these incrementally from existing modules; directory changes alone are not a success criterion.

## How to measure and close work

- The tracker owns task status; this roadmap owns acceptance criteria. All tasks start open. Existing functionality can satisfy a criterion only after its stated proof is attached.
- Each completed task records the change/PR, exact verification command or manual procedure, commit/build, platform, observed result, and evidence location. Assign a person when work starts; role labels below are not assignments.
- A milestone is complete only when its criteria pass for the advertised scope and its dependent tasks are closed. A waiver remains a visible scope change, not a passing test.
- If a target proves impractical, record the measurement, user impact, and revised criterion in a reviewed roadmap change before release. Never silently lower a target after seeing a failure.
- Weekly review: select a small number of ready tasks, update evidence and blockers, inspect platform parity, and re-estimate the next milestone. Track completed criteria rather than a misleading percentage based on task count.

Start with AM001 through AM008 for correctness and AM019 for the platform inventory. The first tangible design deliverable is a native Windows prototype and a native macOS prototype of the same scan-to-evidence journey. The first release deliverable is a green, reproducible engine baseline with correct evidence and current results.
